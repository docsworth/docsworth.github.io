Four moments where it matters. Each one a real Claude Code session.

Docsworth sits between your coding agents and your team's runbooks. Agents cite only pages a team owns and has verified recently, and name the owner of everything else. Fixes and verifications go to the owning team as pull requests. Here is what that looks like across a page's life:

  1. During an incident: answer from what's verified
  2. After the incident: fix the runbook where the next agent reads it
  3. Every quarter: keep a page trusted with one small PR
  4. Day one: start from the docs you already have

Every recording is a real session with the Docsworth plugin on our example repo, a made-up company called Acme. The answers are unedited; only idle time is cut, and a caption band says what each part shows.

During an incident: answer from what's verified

For the on-call engineer, in the service's own repo.

Ask the way you already do. Docsworth's search hands the agent the pages a team has verified inside their review window, each with its owner and date. A page past its review date, a draft, or a deprecated page comes back without its text: just its title, its owner and why it was left out.

Why it helps Nobody checks a runbook's date at 2 a.m. The agent does it for you, every time, and when the page can't be trusted you learn who to call instead of running last spring's steps.

After the incident: fix the runbook where the next agent reads it

For whoever writes the postmortem.

Point Claude Code at the postmortem and ask it to update the runbooks it touched. The plugin's update-after-incident skill finds the affected pages, and propose_edit opens one pull request per page with the exact change and, as its reason, what happened during the incident.

Why it helps Postmortem action items tend to wait in a ticket until the next outage. Here the fix is a small diff in the owning team's review queue within a minute, with the evidence attached. Nothing merges until that team approves it, and Docsworth never writes to your default branch.

Every quarter: keep a page trusted with one small PR

For the team that owns the pages.

docsworth stale --owner-team platform lists the pages a team owns that are past their review date. Someone on the team reads one, fixes what changed, and runs docsworth verify. That moves the page's verified date to today: a one-line change the team reviews like any other pull request.

Why it helps Keeping docs current stops being a project. Each page has a review date and an owner, so the work arrives in small, named pieces, and the moment a page is verified, agents cite it again.

Day one: start from the docs you already have

For a team with markdown docs in a service repo or a docs site.

Copy your docs into a knowledge repo and run docsworth adopt. Each page gets an owner from CODEOWNERS and, with --dates-from, the date its content last changed in the repo it came from. docsworth drafts then lists them newest first: the queue your team verifies from.

Why it helps No migration and no new editor: the pages stay markdown in git. Agents can find drafts from the first hour and name their owners, but cite only what a team has verified, so nothing unchecked is quoted as fact while you work through the queue.
